# Fable 5.2에 맡길 작업 지시문

공통: 먼저 `CLAUDE.md`와 `docs/handoff.md`를 읽고, 그 원칙(화면 안 가리기, 꾸미기 중심, 만족도는 쉽게 100이 되면 안 됨)을 깨지 않는다.
**먼저 계획만 세워 보여 주고 승인을 받은 뒤 실행한다.** 끝나면 `node tests/smoke.js`가 모두 통과해야 하고, 바뀐 수치와 이유를 표로 보고한다. 푸시는 하지 않는다.

---
## 작업 1. 경제·만족도·평판·Level 전체 밸런스 재설계 (가장 추천)
목표: 최근 며칠간 따로따로 조정한 값들(건물 2배, 수입 3배, 만족도 50% 시작, 불편 민감도, 기대치, 평판 감쇠)이 서로 맞물려 의도대로 움직이는지 검증하고, 일관된 밸런스표를 만든다.
1. `tests/` 밖에 `tools/sim.js`(Node, 헤드리스)로 52주 이상 자동 플레이하는 시뮬레이터를 만든다. 게임 코드를 그대로 불러 쓰고 시드를 고정한다. 전략: ① 꾸미기만 ② 매장 중심 ③ 영성·성례 중심 ④ 균형 ⑤ 아무것도 안 함.
2. 주마다 자금·성도·만족도(항목별)·평판·Level·불편 비율을 기록해 표로 낸다.
3. "너무 쉬운 길"(만족도 100, 자금이 계속 남아도는 구간)과 "막히는 구간"(성도가 줄기만 하는 구간)을 찾는다.
4. 끝 기준(수치로): 보통 난이도에서 ① 1년(52주) 안에 목표 4개 ② 만족도 100은 상위 전략에서만, 영성을 안 챙기면 60 아래 ③ 평판 80 유지에 행사·봉사 필요 ④ 자금은 중반에 "무엇을 지을지 고민"할 정도(바닥나지도, 쌓이지도 않게) ⑤ 교회 Lv 10은 약 1년 안, Lv 50 이상은 장기 목표.
5. 상수 조정안을 한 장 표로 제안하고, 승인 후 반영한다.

## 작업 2. 커밋 전체 코드 리뷰와 버그 찾기
`git log`의 `feature/ministry-balance` 전체(약 65개)를 main과 비교해 본다.
- 경계 상황: 데크·10층·경사로·연결 다리·칸 건물·길찾기가 겹치는 곳, 철거·되돌리기·옮기기.
- **돈이 새는 길**: 건물을 짓고 되돌리기/철거해서 이득을 보는 경우, 바닥 바꾸기 환불, 값이 바뀐 뒤 옛 저장의 철거 환불.
- **저장 호환성**: 옛 저장에 새 필드(`fresh`, `evW`, `lvl`, `grip*` 등)가 없을 때 오류가 나는지, `load()`가 채워 주는지.
- 무한 루프·NaN·성능(방문자 많을 때, 큰 데크).
- 결과: 심각도 순 목록 + 각 항목의 재현 방법 + 고친 커밋(고칠 수 있는 것은 테스트를 먼저 추가). 고치기 애매한 것은 질문으로 남긴다.

## 작업 3. 밸런스 상수를 한 곳으로 모으는 구조 정리
- `docs/handoff.md` 7절의 흩어진 상수를 `js/balance.js`(로드 순서 맨 앞쪽) 한 곳으로 모으고, 각 값에 한 줄 주석(무엇이고 올리면 어떻게 되는지)을 단다.
- 동작은 **정확히 그대로**여야 한다: 정리 전후로 작업 1의 시뮬레이터 결과가 같아야 한다(같은 시드).
- 공식 설명 문서 `docs/balance.md`를 만들어 항목별 계산식을 적는다. 현황 화면의 설명 문구가 상수를 읽도록 해 코드와 문장이 어긋나지 않게 한다.
- 전역 이름 충돌과 로드 순서를 조심한다(`tests/smoke.js`의 정적 검사 통과).

## 작업 4. '다음 행동'을 끌어내는 진행 시스템 설계·구현
설계 먼저(문서 1~2쪽), 승인 후 구현.
- 성도들의 바람: 2~3주마다 성도들이 한 가지를 바란다(예: 찬양실, 수련회, 주차 자리). 정해진 주 안에 들어주면 만족·평판 보상, 놓치면 만족 하락. **챙길 일 맨 위에 한 줄**로만 표시(화면을 가리지 않기).
- 매너리즘: 4주 넘게 새 건물·새 행사가 없으면 만족도가 조금씩 내려가고, 새로 하면 풀린다.
- 초반 30분 경험(첫 목표들의 순서와 해금), 교회 Level별 해금·보상 곡선.
- 평가: 작업 1의 시뮬레이터에 "바람 들어주는 플레이어/무시하는 플레이어" 전략을 추가해 차이가 의도대로인지 보인다.
