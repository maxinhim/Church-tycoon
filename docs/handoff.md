# 인수인계: 설계 결정과 지금의 밸런스

대화 기록 없이 이 게임을 이어받는 사람(또는 모델)을 위한 문서입니다. 먼저 `CLAUDE.md`를 읽으세요.
검증은 `node tests/smoke.js` (지금 34개 스크립트 묶음, 전부 통과), 화면 확인은 `python3 -m http.server 8000`.
브랜치 `feature/ministry-balance`, 커밋은 모두 로컬에만 있습니다(푸시하지 않기로 했음).

## 1. 지켜야 할 원칙 (사용자가 정한 것)
- **화면을 가리지 않는다.** 큰 패널·상시 안내 대신 지도 위 작은 카드·버튼·짧은 알림. 길·바닥을 깔 때도 안내 박스 없음(바닥은 ✓ 옆 값만).
- **꾸미기와 건축이 중심.** 자금 스트레스보다 "나만의 교회 공간을 넓혀 가는 재미". 그래서 수입은 넉넉하고, 기능 건물은 비싸고, 꾸미기·바닥·길·지형·편의 소품은 싸다.
- 하지만 **만족도는 쉽게 100이 되면 안 된다.** 여러 방면(영성·편의·교제·주차·돌봄·목양)을 계속 짓고 챙겨야 유지된다. 사용자의 "다음 행동"을 부추기는 것이 목표.
- 문제가 생길 만한 지시는 곧이곧대로 따르지 말고 **반박하고 대안을 제시**, 불확실하면 먼저 질문.
- 모바일 가로 화면 전용, 순수 HTML/CSS/JS, 외부 라이브러리 금지(글꼴만 허용).
- 기존 게임의 그래픽·텍스트·코드를 복사하지 않는다. 이미지는 직접 만든 것·CC0·Gemini 생성물만.

## 2. 시간과 날씨
- 한 주 = 48초(`WEEK`). 월~주일 7일, 주일 끝에 정산. 배속은 테스트 난이도에서만(2·4·8×), 일시정지·1×는 항상.
- 날씨는 주마다 바뀌고, 비·눈은 2~3일만 온다.

## 3. 경제 (js/sim.js, buildings.js, finance.js, ministry.js)
| 항목 | 값 |
|---|---|
| 초기 자금 | 보통 20,000 / 어려움 14,000 / 테스트 50,000 |
| 기능 건물 값 | 원래의 2배 (`BUILD_K=2`: 예배·교제·소모임·매장·돌봄·편의·주차). 칸 건물 위층 1,000 |
| 값이 그대로인 것 | 조경·꾸미기·바닥·길·지형, 그리고 `prop:1`인 편의 소품(벤치·쓰레기통·식수대·정자 등) |
| 주일 헌금 | 출석 × 30 × (0.4+0.6×만족도/100) × 사역 보정 ÷ (1+출석/500) |
| 방문자 헌금 | 방문자 × 3 × (0.5+평판/100) |
| 개척 후원 | 600 − 6 × 주 (100주에 끝) |
| 매장 | 한 번 살 때 `d.income × 8`(`SHOP_K`), 재료비 25%는 판매 순간 바로 나감 |
| 목표 보상 | 800/1,400/2,000/3,000/4,400/6,000/10,000 |
| 대출 | 6,000 / 16,000 / 40,000, 신용 한도 = (8,000+성도×180+평판×120) |
| 노후 | 한 주 0.8 + 이용당 0.008 (관리팀·행정이 줄임), 수리비 = 건물 값 × 10% × 낡은 정도 |
- 한 주 순수익(시뮬레이션): 새 교회 ≈ 1,200, 성도 40명·매장 셋 ≈ 2,000.
- 재정 영수증의 "합계"는 주중에 이미 들어온 매장 수익을 포함한다. 정산 순간의 실제 변동은 영수증의 "정산 때 자금" 줄.

## 4. 성도 만족도 (js/state.js, spirit.js, gripes.js)
- 만족도 = **항목 점수 × 85** + 보너스(꾸밈 + 사역팀·권사·행사 + 최근 일 − 낡은 건물 − 지난주 불편). 항목만으로는 85까지.
- 항목 비중: 영성 25 · 좌석 20 · 목양 17 · 교제 12 · 주차 10 · 돌봄 9 · 편의 7.
- 항목 하나 = (기본 + 건물 자리 × `BLD_SAT`(0.6)) ÷ 필요. 필요 = max(최소값, 성도 × 비율 × 기대치). 기본 = 최소값의 약 절반 → **새 교회는 항목마다 ≈50%, 전체 ≈45에서 시작**.
- 기대치 = 1 + 성도/500 + (교회 Lv−1) × 0.015.
- 영성 = 말씀 30 + 기도 20 + 찬양 20 + 성례 30 (성찬식 8주, 세례식 12주, 수련회 16주 안에 연 것이 점점 줄어듦).
- 꾸밈 보너스 = 아름다움 × 0.15 + 새로 꾸민 것 × 1.0 (최대 +8). 새로 꾸민 것은 한 주 15%씩 줄어든다(익숙해짐).
- 이탈은 만족도 45 아래부터, 소개로 늘기는 50 위부터.
- **방문자 불편**(화장실·배고픔·목마름·외로움·다리·쓰레기·삭막함·붐빔): 방문자가 직접 시설을 찾아가고, 못 찾으면 불편. 지난주 불편 비율 × 11, 최대 −8. 챙길 일에는 방문자 10% 이상(최소 3명)이 겪은 것만 뜬다.
- 교회 문은 예배 공간이 하나는 있어야 열 수 있고, 열려 있는 동안 마지막 예배 공간은 철거 못 한다.

## 5. 평판 / Level
- 평판 주간 변화 = 건물·사역 효과 + (만족도−60)×0.02 − (평판>40이면 (평판−40)×0.08). 방문자 한 명의 영향은 절반. → 80 유지에도 꾸준한 노력 필요.
- 교회 Level(1~100): 점수 = 시설 가치 + 자금×0.2 + 만족도×20 + 성도×50 + 평판×20. Level L 기준 = 10,000 + 800×(L−1)^1.55. 한 번 오르면 안 내려감. 오르면 큰 배지·폭죽(약 2.5초).

## 6. 방문자 행동 (js/visitors.js)
- 건물 선택 비용 = 거리×0.3 + 이번 주 이용/자리×2.5 + 붐빔×4 − 새 건물 끌림 + 무작위 → **고루 쓰이게**. 욕구는 88까지 차야 됐다고 봄. 할 일이 없으면 75%는 바로 귀가.
- 꽉 찬 건물에서 3.5초 기다리면 돌아서고 불만 ×1.5, '붐빔' 불편 무게 1.2.

## 7. 코드 구조 주의
- `js/` 파일은 전역을 공유하고 로드 순서가 있음(`index.html`). 새 파일은 알맞은 자리에 추가하고 `'use strict'`로 시작.
- 건물 id 중복 금지(테스트가 검사). 새 분류 '소모임'(`club`)은 하위 묶음(운동·취미·음악)을 `d.sub`로 가진다.
- 밸런스 상수가 `sim.js`, `state.js`, `spirit.js`, `gripes.js`, `visitors.js`, `ministry.js`, `level.js`, `buildings.js`에 흩어져 있다(작업 3이 이를 모으는 일).
- 그림: 새 소모임 건물은 코드로 그린 임시 그림. Gemini 시트 S1~S3 프롬프트는 `docs/art/sheet-prompts.md`.

## 8. 아직 안 한 것
- 성도들의 바람(2~3주마다 요청, 들어주면 보상), 매너리즘(새 일이 없으면 만족도 하락) — 제안만 했고 넣지 않음.
- 소모임 건물 그림(Gemini 시트 대기), main 병합·PR(사용자가 푸시를 미룸).
